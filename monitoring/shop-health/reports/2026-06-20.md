## What didn't

### 🔴 Retail — POS blocked by expired subscription
- **What happened:** Navigated to POS (`/pos`), attempted to open a shift via Cash Management. The "Open Shift" button was disabled until selecting "Main Warehouse" from the outlet dropdown — fine. But `POST /api/shifts/open` returned **403**. The POS itself would not allow any cart actions because `requireActiveSubscription` middleware is returning a subscription-expired error for this tenant.
- **Why it matters:** This is the "general retail" test shop. It's in a permanently broken state for sales — any real merchant in this situation can't ring up a single item. Read-only mode is the intended behavior for expired subscriptions, but the test shop needs to be renewed to be useful as a health check.
- **Technical detail:** HTTP 403 on `POST /api/shifts/open`. POS cart was functional (empty) but Pay was disabled and POS device registration also returned 403.
- **Action needed:** Renew the `livetestauto` subscription via `/admin` so the retail shop can participate in end-to-end sale testing. This shop was last used for read-only checks only (see Jun 19 report).

### 🟡 Shift variance warning on wholesale (expected, not a bug)
- The old open shift on wholesale had Rs −5,000 variance exceeding the Rs 500 threshold. System correctly blocked close and required a reason + manager PIN. This is working as designed but means every run will hit this variance prompt if the shift isn't closed cleanly after each session.
- **Low priority:** Not a bug. Could be avoided by closing the shift at end of each health check run, but the prompt instructions say not to clean up after ourselves. Document for awareness.

### 🟡 Shift close 400 on wholesale (minor)
- `POST /api/shifts/1/close` returned 400 after providing the variance reason and PIN. The UI still showed the shift close summary and the flow continued cleanly. Likely the shift was already closed from a previous partial run, and the 400 is a "already closed" state conflict — not a real failure.

### 🟡 Restaurant POS — menu items hidden until search
- In restaurant mode, the product grid appeared empty on first open. Typing "a" in the search box revealed all items. This is consistent behavior (search-driven catalog) but could confuse a new cashier who expects items to appear automatically. Not a regression — same behavior on prior manual runs.
