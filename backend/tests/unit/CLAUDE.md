# Unit Tests — Claude Guide

Vitest, no DB, no network. Pure functions and hand-built fake dependencies only. Run:

```bash
npx vitest run backend/tests/unit/
```

Most files use ESM imports (`describe`/`it`/`expect`/`vi`). Several use CommonJS `require()` (directly, or via `createRequire()` from an ESM file) because the module under test is itself CJS — e.g. `dockerfile-pg-dump.test.js`, `inventory-intelligence.test.js`, `pricing-service.test.js`, `tenant-auth-employee-email.test.js`, `tenant-auth-effective-role.test.js`, `services-catalog-scheduler.test.js`, `rentals.test.js`, `rooms.test.js`, `treatment-plans.test.js`, `treatment-folio.test.js`, `services-customer-notify.test.js`, `services-booking-reminders.test.js`, `workers-tenant-job-context.test.js`, `retail-flag-preset.test.js` (mixed — constants are ESM-imported, `require` is used only for a cross-check against `middleware/permissions.js`). No file here uses Jest — the repo's one Jest-syntax file (`reports_accuracy.test.js`) lives under `tests/integration/`, not here.

## The core gotcha: `vi.mock()` is unreliable for CJS `require()`

Many backend modules call `require()` inline inside function bodies/closures rather than at module top-level (`plan-limits.js`, `feature-flags.js`, `catalog-scheduler.js`, etc.). Vitest's `vi.mock()` intercepts the module registry at import time — it does not reliably intercept a `require()` fired later inside a closure, especially against a module with mutable module-level state. Three patterns are used depending on the situation:

### Pattern A (default, most common): real function + fake injected deps
Call the real exported function with a hand-built fake `db` (sometimes `boss`/`pool`/`client`) built from `vi.fn()`. The fake either returns canned rows keyed off a regex/substring match on the SQL string, or just records every call so the test can assert on the exact SQL/param shape. This exercises real logic instead of a stubbed shell, and is the default choice for anything whose only real dependency is Postgres or pg-boss.

Examples: `anomaly-worker.test.js` (stub `db.query` returning a queue of canned responses consumed in call order), `business-modules-checklist.test.js` (a fake db that parses the batched `EXISTS(...)  AS n` SQL and marks a column done when its `FROM` table is in a supplied set), `services-catalog-scheduler.test.js` (fake `db.query`/`db.transaction` recording SQL+params), `workers-tenant-job-context.test.js` (fake `pg.Pool`), `services-booking-reminders.test.js`, `services-customer-notify.test.js` (fake db + an explicit 3rd `deps` arg for `enqueueEmail`/`sendSms`/`sendWhatsApp` — `notify()` takes this deps arg for exactly this reason), `treatment-plans.test.js`/`treatment-folio.test.js`, `rooms.test.js`/`rentals.test.js`, `pricing-service.test.js`, `inventory-intelligence.test.js`, `printer-service.test.js`, `services-tips-w24.test.js`, `services-ai.test.js` (fake Anthropic `client.messages.create`), `promo-engine-price-lock.test.js` (fake db whose `query` returns canned `promotions` rows), `workers-orphan-schema-scan.test.js`, `routes-admin-monitoring-infra-cache.test.js`, `routes-orders-transactions.test.js` (a mini Express app + fake `db.query`, via supertest), `workers-email-worker-boss.test.js` (fake `pg.Pool` + the *real* `withTenantContext` helper — deliberately not mocked, see below), `tenant-auth-effective-role.test.js` / `tenant-auth-employee-email.test.js` (fake `db.query` fed to the real `tenant-auth.js`, loaded fresh via `require.cache` eviction).

### Pattern B: `require.cache` eviction + re-require
When the module under test holds module-level mutable state (an in-memory cache, sliding-window counters) and/or does inline `require()` for its own dependencies, tests delete it from `require.cache` before each case and re-`require()` it fresh. This both resets internal state and lets a differently-shaped fake dependency be substituted (by writing a fake CJS module object into `require.cache` at the resolved absolute path *before* the re-require).

Used in: `middleware.test.js` (`plan-limits.js`, `feature-flags.js`, `tenant-auth.js` — each via `injectCjsMock(absPath, fakeExports)` / `removeCjsMock`), `services.test.js` (`alerting.js`'s sliding-window Map, `email.js`'s lazy Resend singleton — including replacing the cached `resend` package's exports with a fake `Resend` constructor), `tenant-auth-employee-email.test.js` and `tenant-auth-effective-role.test.js` (both evict `middleware/tenant-auth.js` from `require.cache` before each test so `init()` state from a prior test can't bleed through).

### Pattern C: `vi.mock()` + `vi.hoisted()` (only for cleanly ESM-importable deps)
Used in `workers-email-worker-boss.test.js` for peripheral dependencies imported at module top-level (`resend`, `email-templates`, `subscriptions`, `marketing`) — `vi.mock()` works here because these are real top-level imports, not inline `require()`. The worker's actual tenant-scoping logic in the same file still goes through Pattern A (real `withTenantContext` + fake pool), because that's the part under test.

### `vi.stubGlobal`
`services.test.js` uses `vi.stubGlobal("fetch", vi.fn())` to intercept `payment-gateway.js`'s direct `global.fetch` call for the xPay adapter — there's no module boundary to mock since the HTTP call is inline.

**Rule of thumb for new tests**: default to Pattern A. Only reach for `require.cache` eviction if the module has genuinely unavoidable module-level state a fresh fake can't reset. Only use `vi.mock()`/`vi.hoisted()` on dependencies imported at module top-level.

## Drift-guard tests (architecturally important)

These aren't behavioral unit tests — they scan source files or cross-reference config tables and fail when something elsewhere in the codebase falls out of sync. Each one enforces an invariant that nothing else in the type system or CI checks.

- **`business-modules-catalog.test.js`** — bidirectional enforcement for `config/business-modules.js`. The load-bearing check: every key in `DEFAULT_FEATURE_FLAGS` (`middleware/feature-flags.js`) must be classified EXACTLY once — as a card's primary flag, a card `sub_toggle`, or listed in `UNMANAGED_FLAGS` with a reason. A new feature flag added without a catalog decision fails this suite. Also checks: card shape (bucket/title/scope/flags/sub_toggles/depends_on), Bucket A mode pairing (every `VALID_MODE` owned by exactly one card, card flags cover the mode-registry bundle), Bucket C setup fields (`setup_route`, `connected_check`), `depends_on` graph has no cycles and no self-dependency, `classifyFlag`/`isCatalogManagedFlag` agree with the tables, and `presetRecommendedModules` derives sane recommendations for every industry preset without throwing.
- **`business-modules-checklist.test.js`** — two concerns: (1) catalog structure — exactly the covered Bucket A verticals (restaurant, appointments, rentals, rooms_lodging) carry a well-formed `setup_checklist` (each item has `id`/`label`/`required`/`scope`/`route`/`done_query`, outlet-scoped items declare an `outlet_column`, every covered card has at least one required item); (2) `computeChecklists(db, ctx)` — the read-path helper: issues zero queries when no covered card is enabled, computes an enabled card with a **single batched query** (not one-per-item), the required-vs-optional item state rule (a missing required item sets `required_incomplete`, a missing optional one doesn't), the tenant-vs-outlet scope dimension (outlet-scoped items get an `outlet_id = $1` predicate + params, tenant-wide items don't), and a fallback to per-item queries when the batch hits a missing-table error.
- **`feature-flag-consumer-drift.test.js`** — closes the direction the catalog test doesn't cover: being *classified* doesn't prove a flag is ever *read* at runtime. Walks `backend/{routes,services,workers,boot,middleware}` (excluding the flag-declaration file and the two seed-list services) for a whole-token match, and `frontend/src` for a `flags.X`/`posFlags?.X`/`flags["X"]`/`requiredFlag: "X"` gate (the super-admin flag editor's `key === "X"` listing is deliberately not counted as a consumer). Any flag with no consumer must be in a `CONSUMER_EXEMPTIONS` map with a >15-char reason; the suite also fails if an exemption entry is stale (the flag gained a real consumer, or was removed from `DEFAULT_FEATURE_FLAGS` entirely) — forcing cleanup instead of an ever-growing allowlist.
- **`frontend-coverage-drift.test.js`** — the inverse direction again, at the route level: is every backend endpoint reachable from *some* frontend caller? Imports the static cross-reference scanner at `docs/fable5/frontend-coverage-audit/scan.cjs` (`runScan`) and diffs its current dead-route output against a frozen `frontend-coverage-baseline.json`. Fails only when a **new** orphan endpoint appears beyond the baseline (so the class can shrink over time but never silently regrow); a soft check also warns if the baseline has drifted so far from current reality (renamed/deleted routes) that it needs regenerating.
- **`permissions-catalog.test.js`** — the same bidirectional idea applied to permission strings. Walks every file under `backend/routes/` extracting every `requirePerm("x")`, `requireAnyPerm([...])`, and inline `employeePerms.includes("x")` guard string, and asserts each is registered in `config/permissions-catalog.js` (`PERMISSION_IDS`). Also checks every `DEFAULT_ROLE_PERMISSIONS` and `PERMISSION_RULES` entry is registered, that the catalog's `module_key`/`module_keys` linkage agrees bidirectionally with `BUSINESS_MODULES[key].permissions`, and that the delegation permissions (`manage_business_modules`, `manage_integrations`, `manage_roles`, `manage_outlet_modules`) are registered but held by no default role (Administrators pass via `all_access`).
- **`dockerfile-pg-dump.test.js`** — a source-scanning regression guard, not behavioral: `fs.readFileSync`s `backend/Dockerfile` and asserts an `apk add` line installs a `postgresql-client` variant *in the production stage specifically* (after the last `FROM`, not just the builder stage). Guards against `pg_dump` silently missing from the Alpine image, which broke `/api/admin/backup` and `/api/backup/download` end-to-end for an extended period before anyone noticed (R2 had zero backup objects).
- **`tz-date-boundary-guard.test.js`** — walks `routes/`, `services/`, `workers/`, `boot/`, `utils/` line-by-line (skipping comments) with three regex bans: (1) the UTC-"today" idiom `new Date().toISOString().slice(0,10)`/`.substring(...)`/`.split("T")[0]` used as a business "today" — the document-number-datestamp form (`.replace(/-/g, ...)` on the same line) is exempted as cosmetic; (2) bare SQL `CURRENT_DATE`/`now()::date`/`NOW()::date`/`CURRENT_TIMESTAMP::date`; (3) a bare `::date`/`date(col)` cast on a hardcoded list of TIMESTAMPTZ business columns (`session_start`, `check_in`, `received_at`, `timestamp`, `created_at`, etc.) without an `AT TIME ZONE` qualifier. Each rule has a per-file, per-line-substring `ALLOW` allowlist for deliberate UTC/session-day uses (platform cost buckets, dedupe keys, cosmetic datestamps, ORDER-BY-only casts) — every entry needs a one-line justification comment. Read the allowlist before assuming a new hit is a false positive; this is the enforcement mechanism for the tz rules documented in `backend/CLAUDE.md`.

## Other structural patterns

- **Real mini-Express + supertest** for a few route-layer tests: `routes-orders-transactions.test.js` (asserts exact INSERT column list/param order for `POST /api/orders/:id/transactions` — a prior version omitted three columns, causing duplicate rows via a later webhook), `routes-admin-worker-status.test.js` (worker heartbeat endpoint — reads/restores `global.__*WorkerStatus` around each test).
- **Hand-rolled req/res/next stubs, no Express at all** for the rest of the route-handler tests: `routes-admin-monitoring-infra-cache.test.js` (calls the registered handler function directly by pulling it out of a fake `app.get` router; asserts `X-Infra-Cache: hit|miss` header and that a 5-minute in-process cache is respected, bypassed only by `?force=1`), `middleware.test.js`, `feature-flags-modes.test.js` (calls `featureFlags.requireMode(...)` directly against mock req/res/next). Faster, but only valid if the handler doesn't lean on real Express internals beyond what's stubbed.
- **No shared test helpers.** Nothing here imports from `tests/helpers/` (that's integration-test infrastructure — `createTestApp-pg.js`, `request.js`, etc.). Each file builds its own local fakes.
- **Pure functions, no mocking at all**: `tz.test.js`, `utils.test.js`, `utils-ics.test.js`, `mode-registry.test.js`, `industry-config.test.js`, `portal-presets.test.js`, `schemas-shifts.test.js`, `schemas-sales-payments.test.js`, `import-mappers.test.js`, `subscriptions-compute-period.test.js`, `embedded-barcode.test.js`, `retail-flag-preset.test.js` (its `seed*Flags` cases still pass a fake `client`, but the flag-list constants themselves are asserted as pure data).

## Writing a new unit test here

1. Default to Pattern A: call the real function, pass a fake `db`/`boss`/`pool`/`client` built from `vi.fn()`. Assert on both the return value and the recorded call arguments/SQL where the query shape itself matters (column order, param positions, ordering relative to `SET search_path`).
2. Only use `require.cache` eviction if the module has module-level mutable state you need to reset between cases, or does inline `require()` you must intercept with a differently-shaped fake.
3. Only use `vi.mock()`/`vi.hoisted()` for dependencies imported at module top-level — never for inline `require()`.
4. Don't depend on `tests/helpers/` — that's integration-test-only infrastructure. Keep unit tests self-contained with local fakes.
5. If a test guards a specific past production bug, say so in a comment near the assertion (most files here do). It stops a well-meaning "fix" from reverting the guarded behavior by someone unaware of the history.
6. If you're adding a regex/source-scan-style regression guard (like the tz-date-boundary, Dockerfile, or catalog-drift tests), keep the allowlist/exemption mechanism next to the scan and require a one-line justification comment or reason string at each allowlisted entry, not just in the test file.
