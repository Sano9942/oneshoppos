# Routes (top-level domain routes) — Claude Guide

- **~75 top-level route files** — most mounted AFTER tenant middleware (`loadTenantAndPerms` → `resolveTenant` → `loadCompanyProfile` → `resolveContext`) and have `deps.db` (tenant-scoped Postgres proxy), `req.employee`, `req.company`, `req.context`. **Exceptions — mounted BEFORE tenant middleware, no standard session context**: `webhooks.js` (signature-verified only), `receipts.js` (public, manual tenant resolution), `storefront.js` (uses `resolvePublicTenantDb`), `public-restaurant.js` (uses `resolvePublicTenantDb`), `public-bookings.js` (uses `resolvePublicTenantDb`), `country-packs.js` (public, no auth — returns locale/currency config for signup flow), `setup.js` (setup wizard with separate `setupTenantDbManager`), `sandbox.js` (no auth, sandbox payment simulation — only mounted when `PAYMENT_GATEWAY=sandbox`). Never add `req.employee`-dependent logic to these files
- **Subdirectories** (have their own CLAUDE.md): `admin/` (10 files, super-admin), `reports/` (15 files), `shopify/` (9 files), `tier4/` (7 files), `integrations/` (7 files). Also: `customer-portal/` (6 files — auth, data, payments, appointments, stays, treatments; no sub-guide) — mounted before tenant middleware, uses `loadCustomerAuth` + `resolvePublicTenantDb`, serves `/api/portal/*` routes for the end-customer self-service app
- **Orchestrator**: `registerAllRoutes.js` (~607 lines, no route logic) mounts every file under `/api/<domain>`. Never edit for domain changes — only when adding a new route module
- **Auth pattern**: most GET endpoints gated by `requirePerm("view_reports")` or `requireAnyPerm([...])`; mutations gated by domain permission (e.g. `manage_inventory`, `all_access`)
- **Feature-flagged routes**: apply `requireFeature("<flag>")` middleware — current flags include `phase2_draft_orders`, `phase2_pos_approvals`, `phase2_smart_collections`, `phase2_commissions`, `phase2_item_suggestions`, `phase2_outlet_pricing`, `phase2_outlet_tax`, `phase2_outlet_visibility`, `phase2_pos_layouts`, `phase2_report_builder`, `phase2_returns_policy`, `phase2_scheduled_changes`, `phase2_scheduling`, `phase4_appointments`, `phase4_restaurant`, `phase4_restaurant_kds`, `phase4_service_contracts`, `phase4_service_projects`, `phase4_treatment_plans`, `phase4_workflow_tickets` (service-tickets.js), `phase4_rentals` (rentals.js), `phase4_room_management` (rooms.js), `phase5_cod_reconciliation`, `phase5_shipping_automation`, `phase5_sms_providers`, `customer_invoicing`, `customer_messaging`, `marketing_campaigns`, `payment_links`, `subscription_billing`, `fbr_integration`, `ai_insights`, `marketplace_integrations`, `backup_restore` (barcode-expenses.js), `e_invoicing_export` (barcode-expenses.js), `supplier_payables` (grn.js) — see `backend/CLAUDE.md` registry for full list. Note: `price-lists.js` has NO feature flag — gated by `manage_inventory` perm only
- **Validation**: `validate(schema)` middleware applied on mutations where Zod schemas exist in `backend/schemas/` (not yet universal — `routes/couriers.js` remains validation-free; `routes/orders.js` now has partial validation). Many v16 routes (bookings, commissions, contracts, customer-invoices, kds, marketing, projects, restaurant, schedules, smart-collections, subscriptions) use validate() via inline require pattern.
- **Error conventions**: `res.json({...})` for success, `res.status(4xx).json({ error: "..." })` for client errors, `res.status(500).json({ error: err.message })` in catch blocks
- **Transactions**: use `deps.db.transaction(async (client) => {...})` — client inherits the tenant search_path set by the proxy. Reads-outside / writes-inside split is the house pattern for atomicity-critical flows (Phase 4 H2 / DB-5 item 10 Decision LL)
- **Never read** for a domain change: `backend/index.js` (server boot), `registerAllRoutes.js` (orchestrator only). The sub-guide at `backend/CLAUDE.md` documents middleware order
