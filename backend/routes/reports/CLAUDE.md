# backend/routes/reports/

Report endpoints for `/api/reports/*`. Orchestrated by `index.js`, which builds `helpers` once (via `helpers.js`) and passes `(app, deps, helpers)` into each domain module. Almost everything returns JSON — CSV/file generation only happens in `governance.js` (scheduled report delivery), not in the read endpoints themselves.

**Every** route file here now carries an explicit permission guard — the D4 split (PLAN-V2 Step 4, migration v134) retired the single blanket `view_reports` and replaced it with five data-classified splits, so each report is gated on the class of data it returns. Assume a guard is present; the per-file notes below give the exact one. The rough map: `sales.js`/`shifts.js`/`multichannel.js`/`kds-analytics.js` → `view_sales_reports`; `inventory.js`/`stock-aging.js` → `view_inventory_reports` (the latter two also accept `manage_inventory`); `dashboard.js`/`finance.js`/`purchasing.js`/`menu-engineering.js`/`recipe-costing.js` → `view_financial_reports`; `staff.js` → `view_hr_reports`; `clinical.js` → `view_customer_reports` (or `manage_treatment_plans`); `analytics.js` mixes sales/customer/financial per route; `governance.js` → `manage_reports`; `fbr-export.js` → `all_access`. Several files gate on more than one split — check the file, not just this map.

## Wiring (`index.js`)

Registers, in order: `dashboard`, `sales`, `inventory`, `analytics`, `purchasing`, `finance`, `staff`, `shifts`, `governance` (captures its return value), then requires and calls (no return value used) `fbr-export`, `stock-aging`, `multichannel`, `clinical`, `kds-analytics`, `menu-engineering`, `recipe-costing`. `index.js` returns `{ processPendingReportSchedules }` sourced from `governance.js` — consumed by `registerAllRoutes.js`/the report-schedule worker to run due schedules.

## `helpers.js`

Factory `(db) => {...}` called once in `index.js`. Exports:
- **`pgWhere(fragments, params, startIdx=1)`** — the central convention: route handlers push `?`-placeholder fragments onto a `where[]` array as they build filters, then call `pgWhere` once at the end to renumber everything to Postgres `$1, $2, ...`. Returns `{ text, values, nextIdx }` — `nextIdx` matters when you need to append more `$N` params after the WHERE clause (e.g. LIMIT/OFFSET, HAVING).
- **`buildReportFilterParts(req, aliases)`** — the shared "standard" filter builder (voided=false, date_from/date_to via tz-aware UTC bounds, outlet_id CSV, employee_id, category_id via leaf-id expansion). Used by `sales.js` (profit routes) and `analytics.js` (discount-leakage, exceptions). Most other files reimplement their own inline filter-building instead of using this — don't assume it's universal.
- **`buildCategoryMetaMap()` / `withCategoryPaths(rows, meta, sourceKey)`** — resolves `category_id` to full path label via `category-tree.js`. Used throughout inventory/purchasing/sales reports that expose a `category` column.
- **`getDescendantLeafIds(id)`** — category tree leaf expansion, bound to `db`.
- **`parsePaging(req)`** — clamps `limit` (1–500, default 100) and `offset`. Only used by `profit-by-product`.
- **`parseJsonObject`, `nextRunAtIso`, `toCsvLines`** — governance-only helpers (schedule filter JSON parsing, next-run computation, CSV line building with a `# generated_at` / `# filters_applied` comment header).
- **`applyUtcDateFilter` / `applyLocalDateFilter`** — small TIMESTAMPTZ-vs-DATE filter helpers exported for reuse, but most files still hand-roll their own `toUtcStart`/`toUtcEnd` push calls rather than calling these directly.

**Convention**: routes push `?` placeholders and call `pgWhere` (or a local reimplementation of the same idea) rather than writing `$1`/`$2` inline while building filters dynamically — makes it safe to conditionally add/remove WHERE fragments without manually tracking param indices. Several files (`finance.js`'s `pgify()`, `dashboard.js`'s `buildOutletClause()`, `purchasing.js`'s manual `.replace(/\?/g, ...)`) reimplement this pattern locally instead of importing `pgWhere` — don't assume every file shares the same builder.

## Date-param conventions (not consistent across files — check before wiring a new frontend tab)

- **`date_from` / `date_to`** (tenant-local `YYYY-MM-DD`, converted via `toUtcStart`/`toUtcEnd`): the default across most of `sales.js`, `inventory.js`, `analytics.js`, `purchasing.js`, `finance.js`, `staff.js`, `dashboard.js`.
- **`from` / `to`**: `multichannel.js`, `kds-analytics.js`, `recipe-costing.js`. `fbr-export.js` also uses `from`/`to` and makes them **required** (400 if missing).
- **`outlet-comparison`** in `analytics.js` accepts both (`from || date_from`, `to || date_to`).
- **`shifts.js`** uses `date_from`/`date_to` only on `cash-flow`; every other shift route keys off `session_id` (required, 400/404 if missing or not found) via a shared `loadShift(shiftId)` helper.
- `sales.js` additionally supports `time_from`/`time_to` (time-of-day, not date-range) via `applySaleTimeFilters` on several routes — distinct axis from the date filter, both can be applied together.

All date-range filtering against TIMESTAMPTZ columns goes through `toUtcStart(date, tz)`/`toUtcEnd(date, tz)` from `utils/tz.js` with `req.company.timezone` — never a bare `::date` cast (see the tz rules in `backend/CLAUDE.md`). Several files inline-literal the validated tz string into `AT TIME ZONE '${tz}'` for day-bucketing (via `isValidTz()` first) because Postgres requires identical SELECT/GROUP BY expression text — this is intentional, not a SQL-injection gap, but do the same validate-then-inline pattern if you add a new bucketed query.

## Files

**`dashboard.js`** — No `helpers` import (only `(app, deps)`), has its own local `buildOutletClause(col, ids, startIdx)`. `GET /api/reports/dashboard`: one large payload built from ~15 sequential queries (zReport, today/yesterday scalars, profit metrics via tax-exclusive/cost CTEs, expenses, month sales/purchases/refunds, top products, category matrix/contribution, hourly + 7-day + 6-month trends, inventory value/low-stock, attendance summary, per-outlet operational readiness — looped once per outlet, N+1 by design, staff-of-day, cash position). Onboarding-checklist signal queries (`customerCount`, `floorPlanCount`, `bookingCount`, etc.) are each wrapped in their own try/catch so a missing table on an older schema never fails the whole dashboard. Also exports `GET /api/reports/dashboard/wholesale` (A/R outstanding/overdue totals + top 5 buyers, `overdue_days` query param default 30, judged against `tenantToday()` not `CURRENT_DATE`).

**`sales.js`** — Largest file. Shared local helpers: `applySaleTimeFilters` (date_from/to + time_from/to + outlet_id), `applyProductDimensionFilters` (category/brand/supplier/search), `parseComparisonRanges` (derives a matching prior-period window from date_from/date_to). Routes: top-salespeople, sales-summary (tax-by-rate breakdown wrapped in try/catch for pre-v83 deploys missing `tax_rate_at_sale`), sales-detail, order-wise (search param), monthly-mop-matrix, category-wise/subcategory-wise, item-wise (Swagger doc says `from`/`to` but the code actually reads `date_from`/`date_to` — doc/code mismatch, trust the code), brand-wise, customer-wise (no date filter at all), product-performance, performance-workspace (5 parallel queries via `Promise.all`), performance-comparison (manually offsets `$N` params across nested subqueries — fragile, flagged in its own comments, don't touch without re-deriving the index math), refunds-voids, cashier-wise (3 independently-built CTEs concatenated via repeated `pgWhere(..., startIdx)` calls), profit-summary/profit-by-product/profit-by-outlet (all gated `requireFeature("reports_profit_layer")`).

**`inventory.js`** — Returns `{ buildForecastRows }`, reused internally by `replenishment-smart` and exposed via `forecast-demand`. Local helpers: `applyOutletFilter`, `applyInventoryProductFilters`. Routes: sales-stock, inventory-dump (Swagger-documented; `aggregate=1` collapses across outlets into `HAVING`; `anomaly` param selects zero/negative/low stock, zero price/cost, cost-over-sale, margin-risk), product-spec, on-hand (same aggregate/anomaly shape as inventory-dump), inventory-loss, wastage, replenishment (simple threshold), pricing-exceptions, pricing-margin, dead-stock (`inactive_days`, default 90, ungated), forecast-demand (ungated, `formula: "moving_average_daily_velocity"`), replenishment-smart (gated `reports_inventory_health_plus`, filters `days_of_cover < 14`), stockout-risk (gated `reports_inventory_health_plus`, risk_level high/medium/stable buckets), product-movement, str-report, grn-report, history-cost, history-sale, product-audit (schema-hygiene tag scan: missing_barcode/sku/supplier/category, minmax_unset, inactive_with_stock, no_recent_sales — 3 independently-numbered param groups concatenated by sequential index counter), shrinkage (full balance-equation report: `opening = actual - purchases - returns - transfers_in + sales + transfers_out - adjustments`, then `expected` and `variance` derived from that; explicitly separates "restocked" returns (`restock_flag IS NOT FALSE`) from "scrapped" returns (`restock_flag = FALSE`) as two independent shrink vectors).
  - **Note**: a prior shadow duplicate of `/api/reports/stock-aging` that lived in this file (gated behind `reports_inventory_health_plus`) was **removed** — the real stock-aging route now lives solely in `stock-aging.js` and is reachable by every tenant regardless of that flag. If you see references to a "duplicate stock-aging route," that has been fixed; don't re-introduce it.

**`analytics.js`** — comparative-trends (period1 vs period2 revenue/orders), heatmaps (day-of-week × hour density), revenue-leaks (voids+discounts leakage, defaults to a 30-day tenant-local window when no date given — computed via `tenantToday()`, not `toISOString()`, to avoid an off-by-a-day default near midnight), product-mix (market-basket co-occurrence via self-join on `sale_items`), retail-matrix (Star/Plowhorse/Puzzle/Dog via dynamic volume/margin thresholds computed as a separate query first), customer-rfm, customer-details (search param), customer-retention (new/returning/walk-in daily timeline, tz-aware bucketing), customer-capture-rate (per-employee profiled-vs-walk-in ratio), discount-leakage (gated `reports_profit_layer`, uses `buildReportFilterParts`), exceptions (gated `reports_exceptions`; `type` query param selects one of `negative_margin_sales` / `high_discount_orders` / `frequent_voids_by_employee` / `frequent_returns_by_product` — 400 on an unrecognized type), outlet-comparison (accepts both `from`/`to` and `date_from`/`date_to`), supplier-wise, returns-by-reason (date params required — no default window, unlike revenue-leaks/product-mix/retail-matrix/customer-retention/customer-capture-rate in the same file).

**`purchasing.js`** — Local helpers: `applyOutletFilter`, `applyPurchaseProductFilters`, `buildTaxFilter`, `buildStatusFilter`. Uses a manual `?` → `$N` `.replace()` rewrite inline rather than calling `helpers.pgWhere` — same idea, different implementation, so don't assume `pgWhere`-specific behavior (like `nextIdx`) is available here. Routes: total-purchases, itemwise-purchases (both support `tax_mode`=all/gst/no_gst and `status_mode`=all/received/pending/not_received), po-workflow (derives a `workflow_stage` state machine — Draft/Pending Approval/Approved Waiting Receipt/Received Without GRN/Received Not Invoiced/Received Unpaid/Complete — and an "overdue" summary judged against `tenantToday()`), purchase-orders-report (simple read-only PO list), procurement-parity (UNIONs receipts + transfers + adjustments into one timeline, `LIMIT 1000`).

**`staff.js`** — labor-performance (revenue-per-hour via `attendance_sessions.duration_hours`), loss-prevention (void/refund value as % of an employee's valid sales — "risk_ratio_pct"), labor-vs-sales (adds `hourly_rate` × hours = labor_cost), staff-attribution (sales/voids/returns/approvals per employee in one payload). All four default to a 30-day lookback when `date_from` is omitted. Each route builds 2–3 independently-numbered WHERE-param arrays (sale/attendance, or void/refund/sale) and concatenates them in a fixed sequence before renumbering — easy to break param-position if you insert a new filter in the middle rather than appending.

**`finance.js`** — Has its own local `pgify(sql, params)` (parallel reimplementation of `helpers.pgWhere`, no `nextIdx`) and its own `applyRangeFilters(where, params, query, opts, tz)` with a `columnType: "utc" | "local"` switch — `"local"` is for plain `DATE` columns (`expenses.expense_date`), `"utc"` (default) is for TIMESTAMPTZ columns (`grn.received_at`, `supplier_payments.paid_at`) and goes through `toUtcStart`/`toUtcEnd` instead of a bare `::date` cast. Routes: settlement-overview (cash position rollup: inflows via `sale_payments`, outflows via expenses+supplier payments, supplier aging, customer AR), payables-receivables, ar-aging (bucket boundaries come from `req.company.ar_aging_buckets`, validated to be 3 strictly-increasing positive ints, else falls back to `[30,60,90]`; `as_of` validated against a `YYYY-MM-DD` regex, defaults to `tenantToday()`), supplier-payments-invoices (`status=open` means `status <> 'paid'`), finance-payment-mix (daily inflow trend bucketed via inline-literal validated tz), gst-output (line-level inclusive/exclusive/GST split, `LIMIT 500`), gst-type-summary (rolls up output tax from sales vs input tax from GRN receipts into a net-payable-per-rate table).

**`governance.js`** — The only file that does CSV generation, R2 upload, and direct nodemailer sending — everything else in this directory is pure read/JSON. Core function `runSingleSchedule(schedule)`: looks up rows for the schedule's `report_key` via `getRowsForScheduleReport()` (supports `profit-by-product`, `stock-aging`, `stockout-risk`, `eod-digest` — builds an HTML digest via `utils/digestEmail.js` instead of CSV — and `builder:<id>`, which loads a `custom_report_definitions` row and delegates to `report-builder.js:buildQuery()`), converts to CSV via `helpers.toCsvLines()` (or HTML for the digest), uploads to R2, logs to `report_schedule_runs`/`report_delivery_log`, computes the next run via `helpers.nextRunAtIso()`, and — only for `eod-digest` with a valid recipient — sends the digest by email using the tenant's own `email_config` (nodemailer direct, not `services/email.js`; skipped with a logged reason if SMTP isn't configured). `processPendingReportSchedules(limit=5)` is the polling entry point (`next_run_at <= NOW()`), consumed by the report-schedule worker via `index.js`'s return value. CRUD routes for `report_schedules`, `report_schedule_runs` (read-only), `report_delivery_log` (read-only), `saved_report_views` (scope: global/role/personal, resolved against `x-employee-id` header), and `report_definition_versions` (append-only version log) are all gated `requirePerm("manage_reports")` + `requireFeature("reports_scheduled_exports")`, except the saved-views read (`GET /api/reports/saved-views`), which accepts any of the five `view_*_reports` splits or `manage_reports` (still `requireFeature("reports_scheduled_exports")`). The D4 split (PLAN-V2 Step 4) retired `view_reports` and moved this directory off `manage_employees` onto `manage_reports`.

**`shifts.js`** — Shared `loadShift(shiftId)` helper (joins `cash_shifts` + employee/outlet names). cash-flow (date-range, no session_id needed), cash-audit/shift-summary/shift-sales/payment-summary/current-session-zreport (all require `session_id`, 400 if missing, 404 if shift not found), all-denominations (`session_id` optional, reads `shift_denominations`).

**`fbr-export.js`** — `GET /api/reports/fbr-export`, gated `requirePerm("all_access")`. `from`/`to` required (400 if missing). Reads the **frozen per-line tax snapshot** on `sale_items` (`tax_rate_at_sale`, `tax_amount_at_sale`, `hs_code_at_sale`) — deliberately never recomputes against live `taxes`/`products` rows, since FBR filings must match what was actually invoiced. `invoice_date` is derived via `tenantToday(fbrTz, saleTimestamp)`, not a UTC date slice, so a late-night PKT sale doesn't get exported under the wrong calendar day. Returns `{ rows, company }` — CSV conversion happens client-side in the frontend, not here.

**`multichannel.js`** — `registerMultichannelReports`. multichannel-summary (POS + Shopify + WooCommerce side-by-side revenue/discount/tax/AOV), multichannel-daily (per-channel daily trend, merged in JS via a day-keyed `Map`, not SQL UNION), multichannel-products (top products across channels, merged by `product_id` with a name-fallback key for unlinked web items). Web-channel data comes from `web_orders`/`web_order_items`; POS comes from `sales`/`sale_items` — the two are queried separately then joined client-side in JS, never in one SQL statement.

**`clinical.js`** — `registerClinicalReports`. Imports `middleware/feature-flags` and `middleware/permissions` directly (not via `deps`) — a minor inconsistency with the rest of the directory, harmless but note if refactoring. All routes share `gate = [requireFeature("phase4_treatment_plans", { companyLevel: true }), requireAnyPerm(["view_customer_reports", "manage_treatment_plans"])]` — the `companyLevel: true` marker is the Step 9 allowlist: a cross-outlet report stays readable even where the module is off at the viewer's outlet. Routes: plan-completion (by provider), session-attendance (no-show rate), revenue-per-plan (plan-level + session-level averages), patient-retention (30/60/90-day cohort return-rate via `EXISTS` subqueries), lab-turnaround (avg days order→result by lab vendor).

**`kds-analytics.js`** — `registerKdsAnalyticsRoutes`. Gate: `[requireMode("restaurant", { companyLevel: true }), requireFeature("phase4_restaurant_kds_analytics", { companyLevel: true }), requirePerm("view_sales_reports")]` (Step 9 `companyLevel` allowlist — KDS history stays visible where the module is off at the viewer's outlet). Single route `GET /api/reports/kds/prep-times` (`from`/`to`, `station_id`, `outlet_id`): per-station and per-category `p50`/`p95` prep-time percentiles via `PERCENTILE_CONT`, plus recent load-snapshot trend data (`LIMIT 500`) from `kds_station_load_snapshots`.

**`menu-engineering.js`** — `registerMenuEngineeringReport`. Validates query via Zod (`schemas/menu-engineering.js`) before touching the DB — a 400 with `details` on failure, not a raw try/catch 500. Gate: `[requireMode("restaurant", { companyLevel: true }), requireFeature("phase4_restaurant_menu_engineering", { companyLevel: true }), requirePerm("view_financial_reports")]` (Step 9 `companyLevel` allowlist — the analysis spans outlets regardless of where the viewer is standing). Classifies each product into Boston Matrix quadrants (star/plowhorse/puzzle/dog) from popularity (units) vs. avg margin per unit, medians computed in JS (not SQL) over the returned set. A voided line contributes 0 to both popularity and profit; a comped/discounted line still counts toward popularity (customer received the item) but the comp/discount amount is subtracted from revenue before computing profit — driven by `sale_item_adjustments` rows of type `void` vs `comp`/`discount`.

**`recipe-costing.js`** — `registerRecipeCostingReports`. Gate: `[requireFeature("kit_bom_engine", { companyLevel: true }), requirePerm("view_financial_reports")]` — no restaurant-mode gate, since kits/recipes span retail and food-service alike. Uses `from`/`to`/`outlet_id` (not `date_from`/`date_to`). Two routes: `recipe-costing` (per kit/assembled product: plate cost = Σ component qty × *current* component cost, margin, units sold in range, theoretical food cost %) and `recipe-usage` (per component: theoretical quantity consumed = Σ recipe qty × kit units sold — only `'kit'`-type products are counted here, since `'assembled'` products consume their recipe at production time via `stock_conversion_lines`, not at sale). Both responses include a `basis` string stating the limitation explicitly: costing uses the *current* recipe and *current* component cost, not a per-sale snapshot.

**`stock-aging.js`** — `registerStockAgingReport`. Gated `requireAnyPerm(["view_inventory_reports", "manage_inventory"])` — this is the one canonical `stock-aging` implementation (see the note under `inventory.js` about the removed shadow duplicate). Age is computed from the most recent GRN `received_at` per product via a `LATERAL` join; products with no GRN history default to `age_days = 0` (treated as just-received, since `products` has no `created_at` column to fall back on). Buckets: fresh ≤30d, aging ≤60d, old ≤90d, critical >90d. Also returns top-level `total_cost_value`, `avg_cost_per_unit`, `value_at_risk` (sum of stock value for items ≥90 days) computed over the *full* result set regardless of any `bucket` filter applied to the returned `items`.

## Cross-file gotchas

- **Param-index fragility**: several files build multiple independently-numbered `$N` groups (one per CTE or subquery) and concatenate them in a fixed order before running the query — `staff.js`, `sales.js` (cashier-wise, performance-comparison), `inventory.js` (product-audit, shrinkage), `dashboard.js` (every query uses `buildOutletClause` with a manually-tracked `startIdx`). If you add a filter in the middle of one of these instead of appending at the end, you will silently misalign every param after it. Read the existing index math carefully before editing.
- **No single shared WHERE-builder**: `helpers.pgWhere` is the "canonical" version but `finance.js` (`pgify`), `dashboard.js` (`buildOutletClause`), and `purchasing.js` (manual `.replace(/\?/g, ...)`) all reimplement the same `?`→`$N` idea independently. Don't assume behavior from one applies to another (e.g. `nextIdx` tracking only exists in `pgWhere`).
- **Ungated by default**: most routes in `inventory.js`, `analytics.js`, `sales.js`, `purchasing.js`, `staff.js`, `finance.js`, `shifts.js`, `multichannel.js`, `dashboard.js` have no `requireFeature`/`requirePerm` beyond the standard tenant chain. The gated exceptions are explicitly noted per-file above (profit-layer, exceptions, inventory-health-plus, scheduled-exports, treatment-plans, restaurant-menu-engineering/kds-analytics, kit-bom-engine, fbr all_access).
- **Tenant timezone is load-bearing everywhere**: every file that filters or buckets by date reads `req.company?.timezone` (fallback `"UTC"`) and threads it through `toUtcStart`/`toUtcEnd`/`tenantToday`/`isValidTz` from `utils/tz.js`. A new report route that uses `new Date().toISOString().slice(0,10)` or a bare `::date` cast for "today" will reproduce the exact bug class documented in `backend/CLAUDE.md`'s timezone section — don't do that.
