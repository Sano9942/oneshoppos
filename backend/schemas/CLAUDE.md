# schemas/ — Claude Guide

Zod request-body schemas, one file per domain, consumed by the `validate(schema)` middleware factory in `middleware/validate.js` — mounted per-route as `validate(SomeSchema)` between the permission/feature-flag guards and the handler. On success, `validate` **replaces `req.body`** with the parsed/coerced output (stripped of unknown keys unless the schema uses `.passthrough()`); on failure it returns `400 { error, details: [{ field, message }] }`. Handlers must not assume the raw body shape survives — they see the Zod-parsed version.

No schema file imports another. Route files import by destructuring named exports, e.g. `const { CreateSaleSchema } = require("../schemas/sales")`. One-level-deeper route folders (`routes/admin/`, `routes/restaurant/`, `routes/customer-portal/`, `routes/manufacturer-portal/`, `routes/reports/`) use `../../schemas/<domain>`.

Every file in this directory is imported by at least one route file — there is currently no fully-dead schema file (verified by grepping `require(".../schemas/<name>")` across `routes/` for every file listed below). The one exception to "fully used" is at the export level, not the file level (see gotcha below).

## Gotcha: unused exports inside a used file

`admin.js` exports `CreateTenantSchema`/`UpdateTenantSchema`, `CreateAnnouncementSchema`/`UpdateAnnouncementSchema`, `CreateTaxRateSchema`/`UpdateTaxRateSchema`. Only the three `Create*` schemas are wired to a route (`routes/admin/tenants.js`, `routes/admin/messaging.js`, `routes/admin/compliance.js` respectively, POST only — confirmed by grep, zero hits for any `Update*` name anywhere in `routes/`). The three `Update*` variants are empty `.passthrough()` placeholders ("all fields optional — validate in handler") — genuinely dead exports. Don't assume a schema is enforced just because its sibling in the same file is; check the actual route import list before trusting either this note or a past one.

`pos-devices.js` (`RegisterDeviceSchema`, `UpdateDeviceSchema`) was flagged unused by a past audit — that was stale even then. `routes/pos-devices.js` imports and applies both. Re-verify claims like this against a fresh grep rather than repeating a prior note, including this file.

## Conventions across files

- **`.passthrough()` is common** — many schemas only validate the required/critical fields and let extra optional columns ride through untouched. Don't assume a schema without `.passthrough()`; check the file. `.strict()` shows up in a handful of update schemas where the author deliberately wants unknown fields rejected: `rentals.js:updateContractSchema`, `rooms.js:updateBookingSchema`, `service-tickets.js:updateTicketSchema`, `treatment-plans.js:updateSessionSchema`/`updateChartEntrySchema`/`updateLabOrderSchema`, `reservations.js:reservationSeatSchema`, `manufacturer-portal.js:updatePartnerSchema`, `notification-settings.js:rulePatchSchema`/`testSchema`, `forms.js:updateTemplateSchema`.
- **`z.coerce.number()`** is used heavily for anything that might arrive as a string from query params or loosely-typed JSON (IDs, quantities, amounts) — plain `z.number()` shows up in newer/stricter schemas (bookings, rentals, rooms, treatment-plans, restaurant, forms, classes, service-tickets) where the frontend is trusted to send real JSON numbers.
- **Enums as exported constants** — several files export the allowed-value arrays alongside the schema so tests/other routes import the same source of truth instead of re-typing it: `orders.js` (`ORDER_STATUSES`/`PAYMENT_STATUSES`/`FULFILLMENT_STATUSES`), `rentals.js` (`PAYMENT_POLICIES`/`RATE_TYPES`/`ASSET_STATUSES`/`CONTRACT_STATUSES`), `rooms.js` (`OCCUPANCY_STATUSES`/`HOUSEKEEPING_STATUSES`/`BOOKING_STATUSES`/`FOLIO_LINE_TYPES`/`DEPOSIT_STATUSES`), `treatment-plans.js` (`SUBJECT_TYPES`/`PLAN_STATUSES`/`SESSION_STATUSES`/`CONDITION_CODES`/`SEVERITY_LEVELS`/`LAB_STATUSES`/`CONSENT_RELATIONS`/`DOCUMENT_TYPES`/`FOLIO_LINE_TYPES`), `field.js` (`VISIT_OUTCOMES`), `service-tickets.js` (`STATUSES`), `scheduled-changes.js` (`PRODUCT_FIELDS`/`VARIANT_FIELDS`/`CHANGE_TYPES`), `notification-settings.js` (`CHANNELS`), `forms.js` (`FIELD_TYPES`/`ENTITY_SCOPES`/`SUBMITTED_VIA`).
- **`superRefine` over `refine`** for cross-field / dynamic-message validation — anywhere an error message needs to reference the rejected value dynamically, the file uses `ctx.addIssue(...)` inside `superRefine` (see `scheduled-changes.js`, `restaurant.js:createKdsRouteSchema`/`splitCheckSchema`, `rooms.js:createRoomSchema`/`createChannelFeedSchema`, `business-modules.js:OutletToggleSchema`, `classes.js:adminClassBookSchema`, `members.js` public lookup/checkin schemas, `forms.js:fieldSchema`, `field.js` is a plain object with no superRefine despite the domain complexity — worth noting as an outlier). `scheduled-changes.js` explains in a comment why it avoids `refine`'s function-form second argument: Zod 4 dropped it, so dynamic messages require `superRefine`.
- **`create...Schema.partial()`** is the standard way update schemas are derived from create schemas when no extra rules are needed (`rentals.js`, `rooms.js:updateRoomTypeSchema`, `treatment-plans.js:updatePatientSubjectSchema`, `service-tickets.js:updateTicketTypeSchema`, `commissions.js:updatePlanSchema` via `.partial().extend()`, `smart-collections.js:updateCollectionSchema` via `.partial().extend()`). When the update needs different constraints, it's hand-written instead (`treatment-plans.js:updatePlanSchema`, `bookings.js:updateServiceSchema`, `rooms.js:updateRoomSchema` uses `.partial()` on the base but the create variant adds a `superRefine` the update doesn't need).
- **Two-tier "public vs internal" schemas** exist for anything with a public-facing unauthenticated endpoint: `bookings.js` (`publicBookingSchema`), `reservations.js` (`publicReservationCreateSchema`), `rentals.js` (`publicReserveSchema`), `rooms.js` (`publicRoomBookSchema`), `classes.js` (`publicClassBookSchema`/`publicClassWaitlistSchema`), `members.js` (`publicMemberLookupSchema`/`publicMemberCheckinSchema` vs `staffMember*` counterparts — public variants never accept a raw `customer_id`, only unguessable `member_code`/`phone`, so nobody can check in an arbitrary member by counting integer ids), `inquiries.js` (`publicInquirySchema`), `forms.js` (`submitResponseSchema` reached via a public link) — deliberately tighter than their staff-facing counterparts since the caller isn't trusted with fields like `status`/`source`.
- **Reusable line-item / sub-object schemas** get named separately and composed into the parent: `sales.js` (`CartItemSchema`/`PaymentLineSchema`/`PriceOverrideSchema`/`BackorderItemSchema` → `CreateSaleSchema`), `returns.js` (`ReturnItemSchema` → `CreateReturnSchema`), `purchase-orders.js` (`POItemSchema` → `CreatePOSchema`), `customer-invoices.js` (`invoiceItemSchema`/`reminderRuleSchema`), `rentals.js` (`contractLineSchema`, `driverSchema`, `inspectionSchema`, `lineReadingSchema`), `holds.js` (`HoldItemSchema`), `rooms.js` (`bookingGuestSchema`), `treatment-plans.js` (`prescriptionInputSchema`/`vitalSignInputSchema`/`chartEntryInputSchema` reused inside `completeSessionSchema` for the one-transaction SOAP-note+vitals+prescriptions+chart submission, and reused standalone as `createPrescriptionSchema`/`addChartEntrySchema`), `commissions.js`/`smart-collections.js` (`ruleSchema`).
- **PIN/manager-approval fields are validated here but verified in the route handler**, not the schema — e.g. `shifts.js:CloseShiftSchema.variance_approved_by_pin`, `restaurant-void-comp.js:voidCompAdjustSchema.manager_pin`. Don't add PIN-hash comparison logic to a schema file.
- **Portal auth schemas** (`customer-portal.js`, `manufacturer-portal.js`) share the same shape: `emailSchema` (trim+lowercase+email), `passwordSchema` (min 8, max 128), OTP/token schemas. If you fix a validation gap in one, check the other — they're structurally parallel (see `middleware/CLAUDE.md` gotcha on `customer-auth.js`/`manufacturer-auth.js` drifting apart in TTL/status-check details).
- **Aliasing one schema as another's export** when the shape is identical — `classes.js` sets `publicClassWaitlistSchema = publicClassBookSchema` and `adminWaitlistAddSchema = adminClassBookSchema` rather than duplicating the object; `treatment-plans.js` sets `createPrescriptionSchema = prescriptionInputSchema` and `addChartEntrySchema = chartEntryInputSchema`; `rentals.js` sets `updateRentalItemSchema = createRentalItemSchema.partial()`.

## Cross-file relationships worth knowing

- `scheduled-changes.js`'s `CHANGE_TYPES` must stay in sync with the DB CHECK constraint on `scheduled_catalog_changes.change_type` (the file comments the exact schema-pg.sql location) — adding a value here without a matching migration will 500 on INSERT.
- `shifts.js:CloseShiftSchema.variance_approved_by_pin` must stay declared — Zod strips undeclared fields, and its absence once caused close-shift to silently 400 with "Manager PIN required" even when a PIN was submitted. Any schema gating a PIN/approval field is subject to the same trap: if the field isn't in the schema, it never reaches the handler.
- `sales.js:CreateSaleSchema.cartItems[].id/.price` (not `product_id`/`unit_price`) — matches the live API contract documented in the root `CLAUDE.md`. Also carries `field_visit_id`/`field_visit_uuid` (wholesale field sales — pass either, not both), `appointment_id` (F06 POS-from-appointment checkout), `applied_promotions` (wholesale schemes audit snapshot), and `backorder_items` (wholesale backorder creation inside the sale transaction).
- `field.js:CheckInSchema.client_uuid` is the offline-queue idempotency key — the unique constraint on `field_visits.client_uuid` dedupes retries from the IndexedDB queue on the frontend.
- `returns.js`'s inline `ReturnItemSchema` carries serial/warranty fields and per-line restock fields; the restock fields are only honored downstream when the corresponding feature flag is on — the schema itself doesn't gate on the flag.
- Route files in one-level-deeper folders import the same schema file as their sibling top-level route in several domains — e.g. `restaurant.js` (schema) is imported by both `routes/restaurant.js` and `routes/kds.js` for the KDS station/route schemas; `bookings.js` (schema) is imported by both `routes/bookings.js` (staff) and `routes/public-bookings.js` (`publicBookingSchema` only); same public/staff split pattern for `reservations.js`, `rentals.js`, `rooms.js`, `classes.js`, `forms.js`, `members.js`. `menu-engineering.js` is consumed from `routes/reports/menu-engineering.js`, one level under `routes/reports/`.

## Adding a new schema

1. Create `schemas/<domain>.js`, export named Zod objects (`module.exports = { FooSchema, BarSchema }`).
2. In the route file: `const { FooSchema } = require("../schemas/<domain>")` (adjust to `../../schemas/<domain>` for route folders one level deeper).
3. Wire as middleware: `app.post("/api/foo", requirePerm(...), validate(FooSchema), handler)` — `validate` goes after permission/feature-flag checks, before the handler.
4. Prefer `.passthrough()` for create/update bodies with many optional columns you don't want to hand-enumerate; use `.strict()` only when you deliberately want unknown fields rejected.
5. If the schema encodes a DB CHECK constraint (enum, status list), export the array as a named constant so tests and other routes can import the same source of truth instead of re-typing it.
6. Before assuming a schema you're editing is actually enforced, grep the route tree for its import — this directory has at least one precedent (`admin.js`'s `Update*` trio) of an exported schema with zero route consumers.
