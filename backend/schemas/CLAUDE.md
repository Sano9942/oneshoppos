# schemas/ — Claude Guide

Zod request-body schemas, one file per domain. Every schema here is consumed by the `validate(schema)` middleware factory in `middleware/validate.js` — mounted per-route as `validate(SomeSchema)` between the permission/feature-flag guards and the handler. On success, `validate` **replaces `req.body`** with the parsed/coerced output (stripped of unknown keys unless the schema uses `.passthrough()`); on failure it returns `400 { error, details: [{ field, message }] }`. Handlers must not assume the raw body shape survives — they see the Zod-parsed version.

No schema file imports another. Route files import by destructuring named exports, e.g. `const { CreateSaleSchema } = require("../schemas/sales")`.

## Conventions across files

- **`.passthrough()` is common** — many schemas only validate the required/critical fields and let extra optional columns ride through untouched (commented inline with which fields are preserved). Don't assume a schema without `.passthrough()` — check the file; `.strict()` shows up in a handful of update schemas (e.g. `rentals.js:updateContractSchema`, `rooms.js:updateBookingSchema`, `service-tickets.js:updateTicketSchema`, `treatment-plans.js:updateSessionSchema`/`updateChartEntrySchema`/`updateLabOrderSchema`, `reservations.js:reservationSeatSchema`, `manufacturer-portal.js:updatePartnerSchema`) where the author deliberately wants unknown fields rejected.
- **`z.coerce.number()`** is used heavily for anything that might arrive as a string from query params or loosely-typed JSON (IDs, quantities, amounts) — plain `z.number()` shows up in newer/stricter schemas (bookings, rentals, rooms, treatment-plans, restaurant) where the frontend is trusted to send real JSON numbers.
- **Enums as exported constants** — several files export the allowed-value arrays alongside the schema so tests/other routes import the same source of truth instead of re-typing it: `orders.js` (`ORDER_STATUSES`/`PAYMENT_STATUSES`/`FULFILLMENT_STATUSES`), `rentals.js` (`PAYMENT_POLICIES`/`RATE_TYPES`/`ASSET_STATUSES`/`CONTRACT_STATUSES`), `rooms.js` (`OCCUPANCY_STATUSES`/`HOUSEKEEPING_STATUSES`/`BOOKING_STATUSES`/`FOLIO_LINE_TYPES`/`DEPOSIT_STATUSES`), `treatment-plans.js` (`SUBJECT_TYPES`/`PLAN_STATUSES`/`SESSION_STATUSES`/`CONDITION_CODES`/`SEVERITY_LEVELS`/`LAB_STATUSES`/`CONSENT_RELATIONS`/`DOCUMENT_TYPES`/`FOLIO_LINE_TYPES`), `field.js` (`VISIT_OUTCOMES`), `service-tickets.js` (`STATUSES`), `scheduled-changes.js` (`PRODUCT_FIELDS`/`VARIANT_FIELDS`).
- **`superRefine` over `refine`** for cross-field / dynamic-message validation — Zod 4 dropped the function-form second argument to `.refine()`, so anywhere an error message needs to reference the rejected value dynamically, the file uses `ctx.addIssue(...)` inside `superRefine` (see `scheduled-changes.js`, `restaurant.js:createKdsRouteSchema`, `restaurant.js:splitCheckSchema`).
- **`create...Schema.partial()`** is the standard way update schemas are derived from create schemas when no extra rules are needed (`rentals.js`, `rooms.js`). When the update needs different constraints, it's hand-written instead (`treatment-plans.js:updatePlanSchema`, `bookings.js:updateServiceSchema`).
- **Two-tier "public vs internal" schemas** exist for anything with a public-facing unauthenticated endpoint: `bookings.js` (`publicBookingSchema`), `reservations.js` (`publicReservationCreateSchema`) — deliberately tighter than their staff-facing counterparts since the caller isn't trusted with fields like `status`/`source`.
- **Reusable line-item schemas** get named separately and composed into the parent: `sales.js` (`CartItemSchema`/`PaymentLineSchema`/`PriceOverrideSchema` → `CreateSaleSchema`), `returns.js` (`ReturnItemSchema` → `CreateReturnSchema`), `purchase-orders.js` (`POItemSchema` → `CreatePOSchema`), `customer-invoices.js` (`invoiceItemSchema`/`reminderRuleSchema`), `rentals.js` (`contractLineSchema`), `treatment-plans.js` (`prescriptionInputSchema`/`vitalSignInputSchema`/`chartEntryInputSchema` reused inside `completeSessionSchema` for the one-transaction SOAP-note+vitals+prescriptions+chart submission).
- **PIN/manager-approval fields are validated here but verified in the route handler**, not the schema — e.g. `shifts.js:CloseShiftSchema.variance_approved_by_pin`, `restaurant-void-comp.js:voidCompAdjustSchema.manager_pin`. Don't add PIN-hash comparison logic to a schema file.
- **Portal auth schemas** (`customer-portal.js`, `manufacturer-portal.js`) share the same shape: `emailSchema` (trim+lowercase+email), `passwordSchema` (min 8, max 128), OTP/token schemas. If you fix a validation gap in one, check the other — they're structurally parallel (see `middleware/CLAUDE.md` gotcha on `customer-auth.js`/`manufacturer-auth.js` drifting apart in TTL/status-check details).

## Adding a new schema

1. Create `schemas/<domain>.js`, export named Zod objects (`module.exports = { FooSchema, BarSchema }`).
2. In the route file: `const { FooSchema } = require("../schemas/<domain>")` (adjust to `../../schemas/<domain>` for one-level-deeper route folders like `routes/admin/`, `routes/restaurant/`, `routes/customer-portal/`).
3. Wire as middleware: `app.post("/api/foo", requirePerm(...), validate(FooSchema), handler)` — `validate` goes after permission/feature-flag checks, before the handler.
4. Prefer `.passthrough()` for create/update bodies with many optional columns you don't want to hand-enumerate; use `.strict()` only when you deliberately want unknown fields rejected.
5. If the schema encodes a DB CHECK constraint (enum, status list), export the array as a named constant so tests and other routes can import the same source of truth instead of re-typing it.
