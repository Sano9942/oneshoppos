# Fable 5 Playbook — SanoPOS

> How to run Claude Fable 5 productively on this repo. Covers model/effort settings, the working agreement, autonomy policy, verification, and subagent patterns — tuned to SanoPOS specifics (multi-tenant, preset engine, "verify against code not docs" culture).
>
> Companion docs: [build-plan.md](build-plan.md) (what to point it at) · [prompt-templates.md](prompt-templates.md) (reusable task prompts).

---

## 1. Model & effort

- **Model:** switch to `claude-fable-5` (you're on `claude-opus-4-8` by default). The scaffolding here also helps Opus, but Fable 5's autonomy + first-shot correctness is where the leverage is.
- **Effort levels** (Fable 5's primary latency/quality dial):
  - **`high`** — default for feature work, vertical hardening, most tasks.
  - **`xhigh`** — schema/migration changes, multi-tenant routing, security, tax/FBR, anything where a subtle bug is expensive.
  - **`medium`/`low`** — routine edits, label/preset skinning, doc updates, single-file fixes. Even low often beats Opus at high.
- Runs can take many minutes to hours at high/xhigh. Don't babysit synchronously — kick off, let it self-verify, review the result.

## 2. The working agreement (paste-in block)

Drop this at the top of a session or a task prompt. It encodes the Fable-5 behaviors that matter most here. **Do not** put it in `CLAUDE.md` (regenerated by `/audit-docs`).

```
Operating rules for this session:

- Act when you have enough to act. Don't narrate options you won't pursue or re-derive settled facts. If weighing a choice, recommend one, don't survey.
- Scope discipline: change only what the task requires. No refactors, new abstractions, feature flags, or error-handling for cases that can't happen, unless asked. Do the simplest thing that works.
- Verify against code, never docs. CLAUDE.md and memory files drift — confirm every "have/works/missing" claim against actual routes/services/schema-pg.sql, and against the live DB (Supabase MCP) when it's a production-state question. Before reporting progress, point each claim to a tool result from this session; if unverified, say so.
- Audit all call paths for shared concerns. When touching tax, stock, auth, pricing, or visibility, grep every route/service that touches it — the recurring bug here is "POS fixed, storefront/field-rep still broken."
- Boundaries: when I'm asking a question or thinking out loud, give your assessment and stop — don't apply a fix until I ask. Never run migrations against production, never commit or push, never open a PR unless I explicitly say so. Local dev/tests use the local Postgres (.env.test); only touch Supabase for read-only production checks.
- Lead with the outcome. Final message = what happened / what you found first, in plain sentences. Drop the working shorthand; no arrow chains or invented jargon.
```

## 3. Autonomy policy (mixed mode)

**Run autonomously** (Fable 5 plans → executes → self-verifies, no check-in needed):
- Exploring/diagnosing (walkthroughs, grep sweeps, reading code)
- Writing + running tests (Vitest against local PG)
- Preset/label skinning for a new vertical (config-only changes)
- Drafting a fix and its test, then reporting the diff for review

**Pause and get a decision** (end the turn, don't proceed):
- Schema changes / new migrations (`migrate-pg.js`, `schema-pg.sql`)
- Anything touching multi-tenant routing, auth, tax/FBR, or security
- Adding a new **mode** (vs. a new preset on an existing mode)
- Commits, pushes, PRs (per your git-workflow rule)
- Any write to the production DB

For autonomous stretches, add: *"Proceed through reversible steps without asking; only stop for the pause-list items above or when genuinely blocked on input only I can give. Don't end a turn on a 'I'll do X next' promise — do it."*

## 4. Verification — use fresh-context verifier subagents

Fable 5's self-critique is good; **a fresh-context verifier subagent is better** because it hasn't rationalized the implementation. Pattern for any non-trivial change:

1. Main agent implements.
2. Spawn a verifier subagent (general-purpose/Explore) with *only* the spec + the changed files — "confirm X actually works by reading the code and running the test; report discrepancies." It didn't see the implementation reasoning, so it catches wishful thinking.
3. For verticals, the verifier runs the **Playwright walkthrough** against a test tenant (your shop-health pattern) and reports what actually rendered/failed.

SanoPOS-specific verification sources, in order of trust: **live behavior (test tenant walkthrough) > code (routes/services/schema) > tests > CLAUDE.md**.

## 5. Memory — reuse your existing system

You already have the one-lesson-per-file memory system (`.claude/projects/.../memory/` + `MEMORY.md` index) that Fable 5's guidance recommends. Tell it to use it:

> *"When you learn something non-obvious (a correction, a confirmed approach, a gotcha), write it as a memory file per the existing convention and add the MEMORY.md pointer. Don't save what the repo already records."*

The `feedback_*` memories (verify-before-fixing, audit-all-call-paths, SERIAL-pkey trap, field-rep-perm-audit) are exactly the accumulated lessons Fable 5 should read before a build run and add to after.

## 6. Subagent roles on this repo

- **Explore** — locate code, trace call paths, answer "where is X." Use liberally, in parallel.
- **Plan** — design a change before building (schema-touching or cross-cutting work).
- **general-purpose (verifier)** — fresh-context verification + Playwright walkthroughs.
- Delegate independent workstreams in parallel and keep working while they run; intervene only if one goes off track or lacks context. Don't spawn agents for trivial single-file tasks.

---

## 7. Anti-patterns to avoid

- Don't ask Fable 5 to echo/reproduce its internal reasoning as response text — it can trip a refusal category. If you want visibility, read its thinking blocks, don't instruct it to narrate them.
- Don't over-prescribe. Long dos/don'ts lists degrade Fable 5 output; one crisp instruction beats ten. This playbook is intentionally short.
- Don't surface remaining-token countdowns to it mid-run — can trigger premature "let's start a new session" suggestions. If it does, reassure: "you have ample context, continue."
